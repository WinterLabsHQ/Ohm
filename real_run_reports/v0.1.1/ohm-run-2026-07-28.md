**Date:** 28.07.2026
**Ohm version:** 0.1.1 (verified with `ohm --version` at time of writing)
**Agent:** Claude Opus, agentic coding assistant, running in Claude Code

## 0. What this document is

I am an agentic coding assistant. I was given an Ohm project scaffold and a
two-sentence brief, and I drove the toolchain myself: reading the language
reference, reading the compiler's own source, probing its semantics with
throwaway designs, writing the board, iterating against diagnostics, and
verifying the output.

This is a written record of that session — what I was asked, what I thought,
what I ran, what the compiler caught, where I hit friction, and what I could
not do. It is intended as a benchmark artifact, so it includes the rough edges
and the limits. A report that only lists successes would not be useful to
anyone deciding whether to adopt this tool.

Every number in this document was measured during the session, not recalled.

## 1. The brief

The user gave me two instructions, in two messages:

> *"i need to use this ohm to create a board and make it as kicad design."*

and, after the first deliverable:

> *"ok do the next steps."*

That is the entire specification. Everything else was mine to determine.

The starting repository was the stock `ohm init` scaffold: `first-board.ohm`
(an LED, a resistor and a decoupling capacitor), `ohm.toml`, `AGENTS.md`,
`docs/LANGUAGE.md`, and an empty `lib/`.

### 1.1 Resolving the ambiguity

"Create a board" admits two readings that lead to materially different work:
build the existing starter to KiCad, or design a real board. Rather than guess,
I first proved the toolchain worked end-to-end on the starter (`ohm check`
clean, `ohm build` emitting a KiCad project), then asked two questions:

| Question | Answer chosen |
|---|---|
| What board? | **USB-C powered dev board** |
| How far toward manufacturable? | **Add placement constraints** (not through signoff) |

Both answers came back in one round. The second answer set the stage
explicitly at *pre-layout* — which, as §5.3 explains, is what made a
deliberate decision about `mpn=` possible rather than arbitrary.

## 3. Reading before writing

`AGENTS.md` opens with a rule I took literally:

> *"`.ohm` is its own language — not Python, not Starlark, not another HDL. Do not guess syntax."*

So I did not guess. I read, in order:

1. `AGENTS.md` and `docs/LANGUAGE.md` — the authoring contract.
2. The **standard library source** — `std/interfaces.ohm`, `kinds.ohm`,
   `passives.ohm`, `power.ohm`, `connectivity.ohm`, `connectors.ohm`,
   `electromech.ohm`, `discrete.ohm`, `protection.ohm`, `pcb.ohm`.
3. The **compiler's own source** — `ohm.lark` (the grammar), `diagnostics.py`
   (every diagnostic code and its text), `check_intent.py`, `check_bringup.py`,
   `check_mfg.py`, `resolve.py`, `lower.py`, `emit_kicad.py`,
   `emit_constraints.py`, `pkggen/packages.py`.

Reading the checkers before writing the design was the single highest-leverage
decision of the session. Ohm's premise is that declared intent buys you
verification; the corollary is that you should know *what* it verifies before
choosing how to declare things. Knowing that `check_bringup.cap_to_ground()`
looks for any two-pin part with a capacitance `value` whose other pin lands on
a ground net told me precisely how to satisfy `expects cap` — and, later, let
me correctly interpret a check that stayed silent (§7.3).

**Tools used in this phase:** `Read`, `Glob`, `Grep`, `Bash`.

A note on the stdlib source: the comments are unusually honest. Blocks say
things like *"VENDOR-VARIABLE: pad 4 is genuinely variable"* and *"channel
ORDER VARIES BY VENDOR. You MUST check pads 1/3/4/6 against your part's
datasheet"*. For an agent, this is high-value signal — it marks exactly where
the library stops knowing things, which is where I must stop trusting it.

## 4. Probing semantics before committing

`docs/LANGUAGE.md` documents syntax, not checker behaviour. Two modelling
questions would shape the topology, and I did not want to discover the answers
after writing 300 lines. So I wrote a throwaway design in a scratch directory
purely to interrogate the intent checker:

```ohm
module Probe:
    j.V   ~ f.P1
    f.P2  ~ u.VIN         # (c) power_in behind a series element
    u.STRAP ~ j.GND       # (a) input tied straight to ground
    u.PULL  ~ r.P1        # (b) input via a pulldown
    u.EN    ~ j.V         # control: input on a driven rail
```

Result — all three of (a), (b) and (c) raise `I006`; only the control case is
silent:

| Case | Verdict |
|---|---|
| (a) input tied **directly to GND** | `I006` — no driver |
| (b) input via a pulldown resistor | `I006` — no driver |
| (c) `power_in` behind a series polyfuse | `I006` — no driver |
| (control) input on a rail with a `power_out` | silent |

`_DRIVERS` is strictly `{output, power_out}`, and drive does not propagate
through passives — deliberately, per the source comment *"series-R still
floats"*.

**This changed the design.** I had planned a polyfuse in series with VBUS.
Case (c) showed it would leave the regulator input undriven in the intent
model. I dropped the fuse — a Rd/Rd sink is entitled to 500 mA against this
board's 150 mA budget, so the source's own limiter is the real protection —
and kept the TVS clamp, which is passive and does not break the driver path.
That is a design decision the compiler's model provoked, and I recorded the
reasoning in the source next to the regulator.

Twenty minutes of probing prevented a topology I would have had to unpick
later. I would recommend this pattern to anyone driving Ohm from an agent.

## 5. The design

### 5.1 Structure

```
first-board.ohm   351 lines   wiring, closed-form checks, layout intent
lib/parts.ohm     199 lines   datasheet truth: pin maps, pads, ratings
```

The split follows `AGENTS.md` ("reusable blocks go in `lib/`") and, more
importantly, isolates the one class of content no compiler check can validate:
hand-transcribed pad maps.

`lib/parts.ohm` declares five real parts and one kind:

- **`kind Microcontroller`** — my own contract: `requires vdd: power_in`,
  `requires vss: ground`, `optional nrst`, `expects decoupling(10nF, 10uF) on vdd`.
  Written adversarially minimal, following the N3 note in `std/kinds.ohm`.
- **`STM32F103C8T6(Microcontroller)`** — LQFP-48 via
  `generate(QFP, pins=48, pitch=0.5mm, span=9mm)`, all 48 pads mapped.
- **`AP2112K_33(LDO)`** — SOT-23-5, with `v_dropout`, `cin_min`, `cout_min`.
- **`USBC_16P(Connector)`** — 16-pin USB-C, `voltage=5.0V` on VBUS.
- **`USBLC6_2SC6`** — ESD array, deliberately **no kind** (see 5.2).
- **`Crystal_8MHz(Crystal)`** — 8 MHz HSE with `cl=10pF`.

### 5.2 Declaring, and declining to declare

Two decisions are worth recording because they show the honesty model working
in both directions.

**Declining a kind.** `USBLC6_2SC6` is a four-diode steering bridge. `kind TVS`
refines `Diode`, which requires `anode`/`cathode` — a two-terminal shape this
part does not have. I could have forced a binding. Instead I left it as the
base `Component` and wrote why. `std/kinds.ohm` sanctions this directly:
*"A component with NO declared kind is the base `Component` — unchecked...
unknown = unasserted."*

**Declining an operating point.** The USB-C connector's `imax=500mA` is not a
part rating — it is the floor a Rd/Rd sink is entitled to under USB 2.0 Default
Power. A source with a larger Rp allows 1.5 A or 3 A, but this board does not
read CC, so 500 mA is the only figure it may rely on. I declared 500 mA and
documented the reasoning inline, rather than declaring an optimistic number.

### 5.3 The `mpn=` decision

`check_mfg.py` gates the entire DFM/BOM lint behind *"at least one part must
declare `mpn=` or `dnp=`"*, with the comment that DFM lint on a schematic-stage
design *"is pure noise"*.

The user had explicitly scoped this run at pre-layout. I could have invented
plausible manufacturer part numbers to light up the M-codes, but MPNs I am not
certain of are exactly the "invented numbers" `AGENTS.md` forbids. So I
declared **no `mpn=` anywhere**, documented that choice at the top of
`lib/parts.ohm`, and noted in the README that adding any MPN switches on
M001–M008.

I want to flag this as a design tension rather than a clean win: the gate is
well-judged, but it means a schematic-stage board silently gets *no*
manufacturability feedback at all. A `--dfm` opt-in flag would let an author
ask "what would the BOM lint say?" without committing to part numbers.

## 6. Iteration log

Two diagnostics on first compile. That is the entire error list for a 550-line,
39-part design — which I think is the most quotable single fact in this report.

### 6.1 `R012` — a false positive

```
error[R012]: unknown attr 'cl' on component 'Crystal2'
    y1 = Crystal2(freq=8MHz, cl=10pF)
    help: did you mean 'P1'?
```

`std/kinds.ohm` documents `cl` as the intended opt-in:

> *"gated on a declared `cl` attr... **Declare cl= to opt in.**"*

But `R012`'s typo heuristic rejects new component attrs whose name is within
edit distance 2 of a declared attr or pin — and `cl` is distance 2 from pin
`P1`. The documented mechanism is unreachable as an instance override on a
two-pin part.

**Workaround:** I declared `Crystal_8MHz(Crystal)` in `lib/parts.ohm` with `cl`
as a real component attr. This turned out to be the better design anyway — CL
is a property of the crystal you buy, not of one instance — but I arrived there
by working around a bug, not by choosing it. Reported in §12.

### 6.2 `I006` — a true positive I chose to keep

```
warning[I006]: net 'j5.P2' has no driver for its input endpoints: u2.BOOT0
```

BOOT0 is strapped by a 10 k resistor and never driven. The report is correct.
Per §4 this is unavoidable for any strapped digital input, and `I006` has no
waiver mechanism (waivers are a bring-up/`B`-code feature).

I left it visible and documented it in the source and README, rather than
demoting the pin to `role=passive` to silence it. `AGENTS.md` is explicit:
*"Never restructure a design to hide intent."* A strapped configuration pin
genuinely has no active driver, and the compiler saying so is not wrong.

**Final state: 0 errors, 1 intentional warning.** `ohm check` exits 0.

## 7. Not trusting the checker: mutation testing

A checker that passes because it never ran is worse than no checker. `ohm check`
exiting 0 is not evidence on its own, so I deliberately broke the design three
times to confirm each pass was live.

### 7.1 Closed-form assert — fires correctly

Changed the status-LED resistor from 680 Ω to 220 Ω:

```
error[C001]: assert is false: ((v_io - vf_led) / r_stat.value) <= u2.PC13.imax
  — left is [0.005850585058505850585058505851, 0.005968778696051423324150596878] current,
    right is 0.003 current
```

Two things stand out. The evaluation crosses three declaration sites — a module
`config`, an instance `value` with tolerance, and a *pin rating* on a different
component — and folds them into one comparison. And the left side is an
**interval**, not a point: the ±1 % resistor tolerance is propagated exactly,
in `Decimal`. This is the check that makes PC13's 3 mA sink limit a compiler
error instead of a code-review comment.

### 7.2 Bring-up check — fires correctly

Changed a crystal load capacitor from 10 pF to 470 pF. Both passes fired:

```
error[C001]: assert is false: c_x1.value <= ((2 * (cl_xtal - c_stray)) + 2pF)
warning[B008]: 'y1' (Crystal): net 'c_x1.P1' ('a') needs a load capacitor to ground
```

### 7.3 A check that correctly stayed silent

The most informative of the three. I lowered the LDO output capacitor from 1 µF
to 100 nF, expecting `B006` (`cout_min` requires ≥ 1 µF). **Nothing fired.**

My first instinct was that the check was broken. It was not. `cap_to_ground()`
walks *every* two-pin capacitance part on the net, and the 3.3 V rail still
carried a 10 µF bulk capacitor. The rail genuinely met the ≥ 1 µF requirement.
The checker reasons about the **net**, not the instance — which is the correct
electrical model and a stronger guarantee than a per-part rule.

I only knew to reach that conclusion instead of filing a bug because I had read
`check_bringup.py` in §3. I then re-ran the test on an isolated net (7.2), where
it fired as expected.

## 8. Reviewing the netlist — where I found my own bug

`ohm build` succeeding is not evidence the wiring is right. I dumped all 34
nets with their nodes and checked each against intent.

The wiring was correct. But the review surfaced a defect in my **constraints**:

```
d1.IO1_A  [3]  D1.1, J1.A6, J1.B6      <- connector side of D+
d1.IO1_B  [3]  D1.6, R4.1, U2.33       <- MCU side of D+
```

The USBLC6 sits *inline* on the pair — pads 1 and 6 are one internal node, so
the routed differential pair is **two segments**, not one. I had written
`diffpair`/`impedance`/`length` referencing only `u2.PA12`/`u2.PA11`, leaving
the connector-to-ESD segment with no impedance or skew rule at all. A 90 Ω pair
specified on only half its length is not specified.

Fixed by adding a second set of constraints on `j1.DP_A6`/`j1.DM_A7`. Confirmed
in `constraints.json`: two `diffpair`, two `impedance`, two `length` entries.

This is worth noting as a **benchmark observation, not a tool complaint**:
inline two-node protection parts are a topology where net-level constraint
references quietly under-specify. Nothing in the toolchain flagged it. The only
reason it was caught is that I read the emitted netlist rather than trusting a
clean exit code.

## 9. Placement

The second instruction ("do the next steps") meant layout. Two hard limits
established immediately: `ohm --help` shows no `route` or `place` subcommand,
and KiCad is not installed on this host.

Inspecting the emitted board showed only my 7 `fixed` parts were placed; the
other 32 were strung out in a default row from x=14 to x=229 mm — far outside
the intended outline.

### 9.1 Letting the pinout drive the floorplan

I extracted pad coordinates from the generated `QFP-48.kicad_mod`:

```
LEFT   pads 1..12     BOTTOM pads 13..24     RIGHT  pads 25..36     TOP    pads 37..48
```

This exposed a conflict: USB is on pads 32/33 (**right**) while the USB-C
connector sits on the **left** board edge, and the crystal is on pads 5/6
(**left**). Routing a 90 Ω pair around the MCU would be poor.

Rotating `u2` by **180°** resolves it: USB pins face the connector, crystal
pins face the oscillator island on the right. Every other placement follows
from that one decision. This is exactly the kind of choice that should be
driven by measured pad data, not assumption — and Ohm's generated footprints
made that data available to me directly.

### 9.2 Verifying rather than eyeballing

Placing 39 parts by eye is error-prone, so I wrote a verifier that applies
KiCad's rotation transform (`gx = x + px·cosθ + py·sinθ`,
`gy = y − px·sinθ + py·cosθ`) to each footprint box and checks board
containment, pairwise clearance, and every `near()` constraint.

It caught two real errors in my first floorplan:

| Defect | Fix |
|---|---|
| M3 holes 3 mm from edge — screw head overhangs | moved to 4 mm inset |
| `c_nrst` / `r_boot` overlapping by **1.05 mm** | relocated `r_boot` |

I also enlarged the board from 50 × 25 mm to **60 × 30 mm**; at the smaller
size the left region reached ~62 % part density before any routing channels.

Final placement: **39/39 parts**, no overlaps (tightest gap 0.30 mm), all
inside the outline, all 12 `near()` constraints satisfied, and all 39 poses
`locked` in the emitted board and matching the verified plan exactly.

A note for the language: `near()`'s semantics are undefined — centre-to-centre
or edge-to-edge. Under the centre-to-centre reading, `near(c_dec, u2, 2mm)` is
*geometrically impossible* (half a QFP-48 courtyard plus half an 0603 is
already 6.5 mm). I adopted the edge-to-edge reading, which matches the intent
of a decoupling rule, and documented it in the source.

### The board

A USB-C powered STM32F103 development board, 60 × 30 mm, four M3 holes on a
52 × 22 mm pattern.

```
USB-C (5 V, Rd/Rd sink) -> AP2112K-3.3 LDO -> 3.3 V -> STM32F103C8T6 (LQFP-48)
```

USB-C inlet with 5.1 k CC pull-downs and an inline USBLC6-2SC6 ESD array;
regulator with datasheet input/output caps and 10 µF bulk per rail; MCU with
one 100 nF per supply pin, 8 MHz HSE crystal with 10 pF load caps, 1.5 k D+
pull-up for full-speed enumeration, reset button, BOOT0 strap header, SWD
header, power and user LEDs, and 2 × 1×10 GPIO breakout.

## 11. Determinism

`docs/LANGUAGE.md` claims builds are *"hermetic and byte-identical"*. I tested
it rather than quoting it — hashed the outputs, deleted `out/` entirely,
rebuilt, and compared:

```
DETERMINISM: byte-identical across a clean rebuild
```

Confirmed for `.kicad_pcb`, `.net` and `.constraints.json`. For an agentic
workflow this matters more than it might seem: it means a rebuild is never a
source of spurious diff noise, and the emitted board can be committed or
diffed as a review artifact.

## 12. Friction and findings

Offered constructively, in rough priority order.

1. **`R012`'s typo heuristic blocks the documented `cl=` opt-in.** `Crystal2(cl=10pF)`
   is rejected as a typo of pin `P1`, though `std/kinds.ohm` explicitly says
   *"Declare cl= to opt in."* Any two-pin part with a short attr name hits this.
   Suggestion: exempt names that a declared `expects ... when <attr>` references.

2. **`I006` has no waiver, and fires on every strapped input.** Verified by
   probe (§4): even an input tied *directly to ground* is reported as undriven.
   Strapped configuration pins are ubiquitous. The B-codes have `waive=` for
   exactly this reason; I-codes do not. Either a waiver, or a
   "definite level via passive to a rail/ground" refinement, would help.

3. **Library footprints emit as pad-less stubs**, by design
   (`# string-footprint stub: no pads (hydrate in KiCad)`). Consequence I did
   not anticipate: `ohm signoff` on the unrouted board could only trace **2 of
   34 nets** — the rest touch stub footprints and fall under a `V005` note.
   So signoff coverage silently depends on having the KiCad libraries
   installed. Worth stating prominently in the signoff docs.

4. **No board-outline syntax.** `Edge.Cuts` is empty; the outline must be drawn
   by hand in KiCad and is lost on every rebuild, which breaks the otherwise
   clean "source is truth, `out/` is generated" model.

5. **No net-naming syntax.** Net names are structural — the alphabetically
   first pin label wins — so rails come out as `c_bulk3.P1`. I worked around
   it by naming test-point instances in UPPERCASE (`TP_3V3`), since uppercase
   sorts ahead of lowercase instance names. It works, but it is a trick, and I
   had to read `lower.py` to find it.

6. **`near()` semantics are undefined** (centre-to-centre vs edge-to-edge).
   Under one reading, the decoupling constraints in the language reference's
   own idiom are geometrically impossible. Worth pinning down.

7. **`ohm fmt` strips all blank lines.** It is deterministic and canonical, as
   advertised, but on a 350-line design the loss of paragraph structure is a
   real readability cost. Preserving single blank lines between statements
   would keep canonical form without flattening the document.

## 13. What I could not do, and why

I want to be precise about the boundary of this run.

- **Routing was not attempted.** Ohm has no router, and KiCad is not installed
  on this host. I could have scripted copper into the `.kicad_pcb`, but for a
  0.5 mm-pitch QFP-48 with a 90 Ω controlled pair that would have produced
  shorts and unroutable geometry — a board that *looks* finished and must
  never be fabricated. I judged that worse than delivering an honestly
  unrouted board.

- **Signoff is therefore incomplete.** I ran it to confirm the gate works: it
  correctly fails with `V002` on the two traceable USB nets and a `V005` note
  covering the rest. The gate is wired up; it has nothing routed to verify.

- **Library footprint courtyards are nominal.** With KiCad's libraries absent,
  the extents for 17 of 39 parts (USB-C, headers, crystal, switch, LEDs, holes,
  fiducials) are standard values, not measured geometry. My clearance
  verification is exact only for the four generated packages. `j1`'s X position
  in particular assumes the GCT footprint's origin is the connector body
  centre. This needs a DRC pass in KiCad.

- **The MCU pad map is hand-transcribed** from the STM32F103C8T6 datasheet and
  is the one thing in this project no compiler check can validate. A
  transposed VDD/VSS pair is a scrapped board. It is flagged in
  `lib/parts.ohm` and the README as a verify-before-fab item.

The board is a complete, checked, fully-placed schematic-stage design. It is
not fab-ready, and this report should not be read as claiming otherwise.

## 14. Assessment

Ohm's central claim is that declared intent buys verification. On this run it
held up, and the specific shape of the payoff was this: **the checks that
mattered most were ones spanning multiple declaration sites**, which is exactly
where a human reviewer's attention fails.

`(v_io - vf_led) / r_stat.value <= u2.PC13.imax` reaches across a module
config, an instance value with tolerance, and a pin rating on a different
component, and folds them into one interval comparison. Nobody catches that in
review of a 39-part board. The PC13 3 mA sink limit is a classic F103 mistake,
and here it is a compile error.

Three things stood out as genuinely good:

- **The honesty model is real, not marketing.** Undeclared means unchecked, and
  the stdlib says so in its own comments. As an agent, that is what let me
  decline to invent MPNs, decline to force a kind onto the ESD array, and
  declare a conservative USB current floor — and have those be *supported*
  choices rather than gaps I was papering over.
- **Reading the compiler source paid for itself repeatedly** — most sharply in
  §7.3, where it was the difference between filing a false bug report and
  correctly concluding the checker was right and I was wrong.
- **Determinism and the diagnostic quality.** `C001` reporting a tolerance
  interval rather than a point value is the detail that turns an assert from a
  sanity check into an engineering guarantee.

The friction is concentrated in two places: a handful of rough edges in the
resolver's heuristics (§12.1), and the gap between "emitted KiCad project" and
"KiCad project you can route" (§12.3, §12.4). Neither is fundamental. The
second is the one I would prioritise — the pad-less-stub behaviour is correct
and documented, but its effect on signoff coverage is surprising enough that I
only discovered it by reading `emit_kicad.py` after the numbers looked wrong.

For an agentic workflow specifically, the loop that worked was:
**read the checkers → probe the semantics → design to the checks → mutate to
prove they run → read the emitted netlist**. Clean exit codes were the weakest
evidence I gathered all session; the netlist review (§8) and the mutation tests
(§7) each found something that a passing build did not.
